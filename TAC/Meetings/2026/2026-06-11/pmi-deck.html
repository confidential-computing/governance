I

Problem

Threat model

Confidential computing separates two planes

Management plane

  • Cloud control plane
  • Hypervisor and VMM
  • Host administrators

Application plane

  • Firmware and paravisor
  • Operating system
  • Workload

These planes are mutually adversarial.

The problem, named
“

Part of the code running in the User-provided TCB is often injected by the cloud-provider, especially in the case of cVMs: the firmware responsible for the early stages of booting the VM, as well as the virtual TPM used to attest the later boot stages, are typically beyond the control of the user. […]

Attestation of every step of the bootchain is necessary to verify that the entire User-provided TCB has not been compromised by an admin attack, but it is impossible to perform on current cloud offerings for confidential VMs.

— ANSSI, Technical Position Paper on Confidential Computing, v1.0, October 2025

The user-provided TCB
is not user-provided.

Goal

Move guest firmware into the tenant’s software supply chain.

build→scan→version→promote→attest

Firmware should be operated like workload software.

Fair warning

First, we have to clean under the couch.

Common boot today

The platform contract is a conversation

  1. TENANTSubmits kernel, disk image, and config to the cloud/VMM.
  2. HOSTSelects firmware and builds the virtual motherboard.
  3. HOSTSynthesizes ACPI, DTB, HOBs, CPU model, memory map, boot metadata.
  4. HOSTStarts the guest firmware.
  5. GUESTFirmware queries the host: fw_cfg, CPUID, tables, metadata.
  6. HOSTReturns platform details.
  7. GUESTFirmware hands the synthesized platform description to the OS; the workload boots.
  8. GUESTThe OS executes the host’s AML — at boot, and on every ACPI event thereafter.
  9. VERIFIERReceives evidence whose meaning depends on provider-shaped boot context.

The boot contract is discovered dynamically by talking to the management plane.

Obstacle

Two bonds hold firmware to the hypervisor.

1 · Tight coupling

Firmware is not portable code in isolation — it is written against a virtual motherboard.

memory mapinterruptstimersPCI / MMIOreset state

2 · Implicit contract

Hypervisors bolted proprietary host ↔ firmware channels onto it — unstated, unversioned.

fw_cfgtable loaderCMOSmagic ports

Both are avenues for the VMM to attack the guest.

Uh oh

Executable code is crossing the boundary.

The host doesn’t just hand the guest data — it hands it code, and the guest runs it blind.

The trap

Trust the answers, or measure them. Pick your poison.

Trust them

Every dynamic answer from the management plane is adversarial input — parsed, mapped, and executed by the guest at full privilege.

executed: AML  ·  parsed: tables  ·  trusted: maps

COSTGuest integrity — the security confidential computing exists to provide.

Measure them

Host decisions fold into the guest’s identity — the same image attests differently on every hypervisor, memory size, and VMM version.

ACPI → vTPM PCRs  ·  TD HOB → RTMR[0]

COSTPortable attestation — one image, a different measurement everywhere.

Either way, the tenant pays.

Good news

The virtual motherboards are converging.

Historically, platform variation made this problem enormous. Standard hypervisor APIs across the major platforms now constrain the virtual motherboard to a narrow set of choices.

  • BOND 1
    Weakened.Convergence leaves far less coupling variation to handle.
  • BOND 2
    Eliminate it.Replace the implicit, unstated channels with an explicit contract.
  • AML
    Kill it.No executable code across the boundary. None.

The prize is bigger than trust and identity: micro-VM or full VM becomes the tenant’s choice — not the hypervisor’s.

Requirements

Negotiate the whole platform — before the guest runs.

Built from existing standards and formats — so the contract is a format for describing the platform, and the format must be:

  • WELL-DEFINED
    Typed, versioned, rejectable when unknown.The implicit contract, eliminated.
  • CONVERTIBLE
    Renders into what the OS already expects.ACPI or Devicetree — not a new universe of hardware description.
  • NO CODE
    MUST NOT contain executable code.AML does not survive this rule.
  • SPLIT TRUST
    Divides host and guest responsibilities.Allocation and definition, separated explicitly.
The missing artifact

A portable, image-owned launch contract

It needs to say:

  • Load these sections.
  • Fill these regions.
  • Require this CPU baseline.
  • Initialize this state.
  • Finalize this target.
  • Start here.
III

PMI

PMI is a launch contract you can ship: platform definition, boot payloads, and per-target launch recipes in one artifact.

Image anatomy

One PE file: payloads, plus multiple target contracts

PE / COFF HEADERS
CODE / DATA

.ovmf guest firmware
.linux kernel
.initrd initrd
PLATFORM DEFINITION

Code & data. The bytes the guest runs — shared across targets rather than duplicated per target.

Platform definition. The measured base Devicetree: the board the image drew.

Launch recipes. One CBOR contract per target, non-loaded — other loaders ignore them, so the same file still boots bare metal as a UKI.

The VMM reads only the section for the target it launches.

One target · .pmi.sev

Anatomy of a target

{
  "version": 1,
  "cpu:profile": "x86-64-v3",
  "sev:id": {"block": ".sev.id.block", "auth": ".sev.id.auth"},
  "merged:dtb": ".dtb",
  "actions": [
    {"type": "load", "gpa": 0x8000000,  "section": ".svsm"},
    {"type": "load", "gpa": 0xFFC00000, "section": ".ovmf"},
    {"type": "load", "gpa": 0x1000000,  "section": ".linux"},
    {"type": "load", "gpa": 0x4000000,  "section": ".initrd"},
    {"type": "load", "gpa": 0x2000000,  "section": ".cmdline"},
    {"type": "load", "gpa": 0x2001000,  "section": ".dtb"},
    {"type": "fill", "gpa": 0x2011000,  "section": ".dtbo", "kind": "merged:dtbo"},
    {"type": "fill", "gpa": 0x2021000,  "section": ".sev.secrets", "kind": "sev:secrets"},
    {"type": "fill", "gpa": 0x2022000,  "section": ".sev.cpuid", "kind": "sev:cpuid"},
    {"type": "load", "gpa": 0x2023000,  "section": ".sev.vmsa", "kind": "sev:vmsa"}
  ]
}

Two actions only — load places image bytes; fill reserves host-populated regions. Anything unknown fails the launch.

The same recipe, executed

What the VMM does with it

  1. startSNP_LAUNCH_START · host policy verified against .sev.id
  2. load.svsm · measured
  3. load.ovmf · measured
  4. load.linux · measured
  5. load.initrd · measured
  6. load.cmdline · measured
  7. load.dtb · measured base platform
  8. fill.dtbo · host allocation overlay, unmeasured
  9. fill.sev.secrets · PSP-populated
  10. fill.sev.cpuid · PSP-populated
  11. load.sev.vmsa · measured BSP register state
  12. finishSNP_LAUNCH_FINISH · locks the launch digest

Three components previously provisioned and attested separately ship as one tenant-owned image.

Definition on the left: which devices exist and where. Allocation on the right: how much memory, how many CPUs — allowlisted, guest-validated, then merged. The OS receives one normal Devicetree.

The motherboard, inverted

The image draws the board. The host fills the slots.

The image draws the board. Which sockets exist, where they sit, what the firmware expects — measured platform definition.

The host populates it. vCPUs into the socket, memory into the slots, virtio-mmio and PCI devices — emulated or passthrough.

Never beyond the board. No slot in the definition, no device in the guest.

Shape is definition. Population is allocation.

Describing the board

Why Devicetree? Run the requirements.

ACPI

WELL-DEFINED✓

Specified and versioned.

CONVERTIBLE✗

One-way. AML cannot be lowered to data — ACPI does not convert to Devicetree.

NO CODE✗

AML is structural. The DSDT is mandatory — the roach is load-bearing.

SPLIT TRUST✗

Monolithic tables interleave definition with allocation.

Devicetree

WELL-DEFINED✓

DT spec; strict parsers in libfdt and safe Rust.

CONVERTIBLE✓

Serves both. Native on aarch64; firmware renders ACPI in-guest on x86.

NO CODE✓

Data only, by construction.

SPLIT TRUST✓

Overlays are a native primitive — DTBO is how DT already splits.

The OS can still receive ACPI — firmware translates in-guest. The trust decision happens before that handoff.

What this does to guests

The guest stops asking.

No longer trusts

  • fw_cfg, CMOS, magic ports — gone
  • Host-synthesized tables and metadata
  • Executable code from the boundary

Now validates

  • Measured base platform from its own image
  • Host overlay checked against the allowlist, then merged
  • Normal Devicetree or ACPI handed to the OS

The same guest image boots on any conforming VMM — and attests identically on all of them.

Payoff

Before / with PMI

The ownership boundary moves

Before

  • Provider selects firmware
  • Firmware queries the VMM
  • Host synthesizes the platform description
  • Launch behavior is implicit
  • Attestation is provider-shaped

With PMI

  • Tenant ships firmware
  • Contract exists before boot
  • Tenant base + constrained host allocation
  • Launch recipe is explicit
  • Evidence maps to the tenant artifact
Payoff

Guest firmware becomes tenant software.

The VM image becomes the unit of firmware ownership, launch, and verification.
